# Scenario 02 — Priority Tiers

## Purpose

Demonstrates that flow control correctly differentiates traffic across three
tiers (**premium**, **standard**, **low-priority**) under concurrent load. The key
question: does higher-priority traffic maintain acceptable latency while
lower-priority traffic absorbs the pressure?

## What It Does

Runs three concurrent traffic streams, each targeting a different
InferenceObjective via the `x-llm-d-inference-objective` header:

| Stream | Tier | Priority | Concurrency | Tokens (in/out) |
|--------|------|----------|-------------|-----------------|
| 1 | premium | 100 | 10 | 128 / 64 |
| 2 | standard | 0 | 20 | 512 / 256 |
| 3 | low-priority | -1 | 20 | 1024 / 512 |

Total concurrent requests: **50** — enough to push the system into saturation
with 2 vLLM replicas.

## How to Run

```bash
./benchmarks/scenarios/02-priority-tiers/run.sh
```

## How to Interpret Results

- **Premium stream**: Should show the lowest TTFT and e2e latency. Even under
  heavy load, its 200-slot budget and priority 100 should insulate it from
  the pressure generated by the other two streams.
- **Standard stream**: Moderate latency, some queuing expected. Check
  `llm_d_flow_control_inflight_requests{priority_band="0"}` in Grafana.
- **Low-priority stream**: Highest latency and most shedding. This tier has only
  50 slots and priority -1, so it gets squeezed first. Check
  `llm_d_flow_control_shed_requests_total{priority_band="-1"}`.
- **Cross-tier isolation**: The critical metric is that premium latency
  remains stable even as low-priority shedding increases. This proves the priority
  system is working.

## Expected Behavior

Under saturation, the low-priority tier should experience significant shedding while
the premium tier remains largely unaffected. The standard tier should see
moderate queuing. If all three tiers degrade equally, the priority
configuration is not taking effect.
