How it works

Saturation: two paths through the system

Flow control is a centralized priority queue between gateway and backends — it only activates when the pool is saturated.

🟢 Below saturation

Requests route directly to the best-scoring vLLM backend. No flow-control queuing — vLLM handles its own internal scheduling.

🟡 At saturation

Requests enter priority queues. Dispatched in strict priority → fairness → FCFS order.

📡

Saturation detection

Two pluggable detectors determine when the pool is saturated:

  • Concurrency-based — in-flight requests ÷ pool capacity. At ratio 1.0, flow control engages. (default)
  • Utilization-based — monitors GPU / KV-cache utilization across backends. Engages when aggregate utilization exceeds a configured threshold.

How it works

Priority, fairness, ordering

A strict 3-tier dispatch hierarchy determines which request is served next.

1

Priority

Scan bands top-down: Premium (100) → Standard (0) → Low (−1).

2

Fairness

Within a band, round-robin across tenants. Equal dispatch rate regardless of volume.

3

Ordering

Within a tenant queue, first-come-first-served. Deterministic and starvation-free.

How it works

Two headers, zero code changes

Priority and fairness are expressed as HTTP headers on the OpenAI-compatible request. No SDK, no app changes.

POST /v1/chat/completions HTTP/1.1 Host: llm-gateway.internal Authorization: Bearer sk-… Content-Type: application/json x-llm-d-inference-objective: realtime ← Priority band x-llm-d-inference-fairness-id: team-alpha ← Fairness ID {"model":"llama-3-70b","messages":[…]}

Maps to a priority tier: realtime → 100 · standard → 0 · low-priority → −1

Arbitrary string identifying the tenant or workload stream — used for intra-tier fair-share scheduling.

No objective header?

Defaults to priority 0 (Standard tier).

No fairness header?

Assigned to the default-flow queue.

⚠

Trust assumption: Flow control assumes clients can be trusted with these headers. In a shared environment, an API gateway or admission policy should validate and inject headers on behalf of callers rather than letting end-users set them directly.

Limitations & operational considerations

Flow control is not a silver bullet

Complement, don't replace, scaling
Flow control manages demand — it cannot add capacity. Pair it with autoscaling, right-sizing, and hardware provisioning for a complete ops strategy.
Keep critical workloads separate
If a workload truly cannot tolerate queuing or deprioritization — even briefly — run it on a dedicated pool. Flow control is best-effort, not guaranteed isolation.
Adaptation is not instant
The EPP reacts to saturation signals, but there is an inherent feedback loop. Expect a brief adjustment window when load spikes or shifts suddenly.
Settings aren't set-and-forget
Priority tiers, fairness weights, and queue depths reflect your current traffic mix. When usage patterns change — new tenants, seasonal surges, model swaps — revisit and re-tune.

Bottom line: Flow control is one layer in a defense-in-depth approach to GPU operations — it works best alongside autoscaling, capacity planning, and dedicated pools for truly mission-critical work.
